==================================================================
 RESUMO DE ESTUDO: como o MySQL inicializa o banco com Docker
==================================================================

Leitura oficial (em inglês): seção "Initializing a fresh instance"
em https://hub.docker.com/_/mysql

Trecho original da documentação:

    "When a container is started for the first time, a new database
    with the specified name will be created and initialized with the
    provided configuration variables. Furthermore, it will execute
    files with extensions .sh, .sql and .sql.gz that are found in
    /docker-entrypoint-initdb.d. Files will be executed in alphabetical
    order. You can easily populate your mysql services by mounting a
    SQL dump into that directory and provide custom images with
    contributed data. SQL files will be imported by default to the
    database specified by the MYSQL_DATABASE variable."

Tradução:

    "Quando um container é iniciado pela primeira vez, um novo banco
    de dados com o nome especificado será criado e inicializado com
    as variáveis de configuração fornecidas. Além disso, serão
    executados os arquivos com extensão .sh, .sql e .sql.gz que
    estiverem em /docker-entrypoint-initdb.d. Os arquivos serão
    executados em ordem alfabética. Você pode facilmente popular seus
    serviços MySQL montando um dump SQL nesse diretório e fornecendo
    imagens personalizadas com dados próprios. Os arquivos SQL serão
    importados, por padrão, para o banco de dados especificado na
    variável MYSQL_DATABASE."

------------------------------------------------------------------
 1. O que isso significa?
------------------------------------------------------------------

- Quando o container do MySQL sobe pela PRIMEIRA VEZ, ele cria o
  banco (MYSQL_DATABASE) e executa qualquer arquivo .sql que esteja
  montado em /docker-entrypoint-initdb.d

- No nosso projeto, isso é feito por esta linha do compose.yaml:

      - ./init.sql:/docker-entrypoint-initdb.d/init.sql

  Ou seja, no nosso caso, o init.sql roda automaticamente e cria/popula a tabela
  book dentro do banco db_books.

------------------------------------------------------------------
 2. A regra mais importante: init.sql só roda UMA VEZ
------------------------------------------------------------------

Os dados do MySQL não ficam soltos no container. Eles são gravados
em um volume do Docker (no nosso caso, vol_books), que existe
separado do container.

Por isso:

  - Se você apagar o container (docker compose down, sem a flag -v) e subir
    de novo, o volume continua existindo com os dados antigos.
  - O MySQL enxerga que o banco já existe e NÃO executa o init.sql
    de novo.
  - Isso é uma proteção: evita que seus dados sejam apagados ou
    sobrescritos sem querer toda vez que o container reinicia.

Resumindo: container é descartável, o volume é o que guarda o estado.

------------------------------------------------------------------
 3. Quando o init.sql é executado de novo?
------------------------------------------------------------------

Apenas quando o volume NÃO EXISTE ainda (volume novo/limpo).

Para forçar isso, é preciso remover o volume existente, não só o container:

    docker compose down       # para e remove o container (mantém o volume)
    docker compose down -v    # para e remove o container E TAMBÉM o volume

Depois, ao rodar novamente:

    docker compose up -d

o Docker cria um volume vazio, o MySQL entende que é uma primeira
inicialização e o init.sql roda de novo do zero.

------------------------------------------------------------------
 4. Comandos úteis para praticar
------------------------------------------------------------------

# Ver os volumes existentes no seu computador
docker volume ls

# Remover um volume específico manualmente (container já parado)
docker volume rm vol_books

# Subir tudo do zero (cria volume novo + roda init.sql de novo)
docker compose down -v
docker compose up -d

# Conferir se os dados iniciais foram criados
docker exec db mysql -u root -psecret db_books -e "SELECT * FROM book;"

------------------------------------------------------------------
 5. Em síntese
------------------------------------------------------------------

| Ação                          | init.sql roda de novo? |
|-------------------------------|-------------------------|
| docker compose stop->start    | Não                     |
| docker compose down (sem -v)  | Não                     |
| docker compose down -v        | Sim (na próxima subida) |
| docker volume rm vol_books    | Sim (na próxima subida) |

E lembre-se: por que remover só o container não é
suficiente para reiniciar os dados do banco? Porque quem guarda os
dados é o volume, não o container.
